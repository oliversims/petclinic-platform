# Secret Rotation

**Last Updated:** 2026-09-02

Manual rotation procedures for the two secrets this platform holds. Rotation is
deliberately manual — there is no `aws_secretsmanager_secret_rotation` resource and no
Lambda rotator. See [ADR-0011](./adr/0011-secrets-manager.md).

## How secrets reach pods

```
AWS Secrets Manager          External Secrets Operator        Pod
petclinic/{env}/*     ──►    ExternalSecret CR (1h refresh)   env var
                             ──► Kubernetes Secret
```

| AWS secret | K8s Secret | Keys | Consumed by |
|------------|-----------|------|-------------|
| `petclinic/{env}/rds-credentials` | `rds-credentials` | `username`, `password` | customers, visits, vets |
| `petclinic/{env}/openai-api-key` | `openai-api-key` | `OPENAI_API_KEY` | genai-service |

Two facts that determine every procedure below:

- **ESO refreshes hourly.** A changed value in AWS reaches the Kubernetes Secret within
  an hour, or immediately if you force a refresh.
- **Spring reads environment variables at startup.** Updating the Kubernetes Secret does
  not change a running pod. The pods must restart.

Values live only in AWS. Nothing here is ever committed — `*.tfvars` is gitignored, and
the ExternalSecret CRs in `k8s/base/external-secrets/` contain references, not values.

### Procedure: Rotate the OpenAI API key

**When:** Key suspected exposed, staff change, or scheduled rotation.
**Who:** Engineer with Secrets Manager write access and cluster access.
**Time:** 15 minutes, including pod restart.

**Steps:**

1. Create a new key in the OpenAI dashboard. Keep the old one active until step 6 —
   revoking first causes an outage.

2. Write the new value to Secrets Manager. Use a file so the key never lands in shell
   history:

   ```bash
   # Write the key to a temporary file (no trailing newline), then:
   aws secretsmanager put-secret-value \
     --secret-id petclinic/{env}/openai-api-key \
     --secret-string file://./new-key.txt \
     --region us-east-1

   shred -u ./new-key.txt      # or: rm -P ./new-key.txt
   ```

3. Confirm the new version is staged as current:

   ```bash
   aws secretsmanager describe-secret \
     --secret-id petclinic/{env}/openai-api-key \
     --region us-east-1 \
     --query 'VersionIdsToStages'
   ```

4. Force ESO to sync rather than waiting an hour:

   ```bash
   kubectl annotate externalsecret openai-api-key -n petclinic-{env} \
     force-sync=$(date +%s) --overwrite
   kubectl get externalsecret openai-api-key -n petclinic-{env}
   ```

   `STATUS` should read `SecretSynced`.

5. Restart the consumer so it picks up the new environment variable:

   ```bash
   kubectl rollout restart deployment/genai-service -n petclinic-{env}
   kubectl rollout status deployment/genai-service -n petclinic-{env} --timeout=5m
   ```

6. Only once the service is confirmed healthy, revoke the old key in the OpenAI
   dashboard.

**Verify:**

```bash
kubectl get pods -n petclinic-{env} -l app.kubernetes.io/name=genai-service
kubectl logs deployment/genai-service -n petclinic-{env} --tail=50 | grep -i -E "openai|401|unauthorized"
```

No authentication errors, and a chat request through the app succeeds.

**Rollback:** Secrets Manager keeps previous versions. Move the `AWSCURRENT` stage back:

```bash
aws secretsmanager update-secret-version-stage \
  --secret-id petclinic/{env}/openai-api-key \
  --version-stage AWSCURRENT \
  --move-to-version-id {previous-version-id} \
  --remove-from-version-id {new-version-id} \
  --region us-east-1
```

Then repeat steps 4 and 5. This only works if the old key was not yet revoked — which is
why revocation is last.

### Procedure: Rotate the RDS master password

**When:** Password suspected exposed, staff change, or scheduled rotation.
**Who:** Senior engineer. This one has a brief window where the app cannot reach the
database.
**Time:** 30 minutes. Expect a short interruption for the three data services.

> **Why this is not a Terraform change.** The password is generated by `random_password`
> and stored in state. Changing it via Terraform would rewrite state and could recreate
> resources. The steps below change the password in RDS and in Secrets Manager directly,
> then bring Terraform back into agreement.

**Steps:**

1. Generate a new password. RDS rejects `/`, `@`, `"`, and spaces:

   ```bash
   openssl rand -base64 32 | tr -d '/@" \n' | cut -c1-24
   ```

2. Change it on the instance. This is the point of no return; apply immediately rather
   than during the next maintenance window:

   ```bash
   aws rds modify-db-instance \
     --db-instance-identifier petclinic-{env}-mysql \
     --master-user-password '{new-password}' \
     --apply-immediately \
     --region us-east-1
   ```

3. Wait for the instance to settle:

   ```bash
   aws rds wait db-instance-available \
     --db-instance-identifier petclinic-{env}-mysql --region us-east-1
   ```

4. Update Secrets Manager with the whole JSON document — both keys, or the app loses the
   username:

   ```bash
   # Write {"username":"petclinic","password":"{new-password}"} to new-creds.json, then:
   aws secretsmanager put-secret-value \
     --secret-id petclinic/{env}/rds-credentials \
     --secret-string file://./new-creds.json \
     --region us-east-1

   shred -u ./new-creds.json
   ```

5. Force ESO to sync:

   ```bash
   kubectl annotate externalsecret rds-credentials -n petclinic-{env} \
     force-sync=$(date +%s) --overwrite
   kubectl get externalsecret rds-credentials -n petclinic-{env}
   ```

6. Restart all three data services:

   ```bash
   for svc in customers-service visits-service vets-service; do
     kubectl rollout restart deployment/$svc -n petclinic-{env}
   done

   for svc in customers-service visits-service vets-service; do
     kubectl rollout status deployment/$svc -n petclinic-{env} --timeout=5m
   done
   ```

7. Reconcile Terraform. State still holds the old generated password, so the next plan
   will want to reset it. Refresh state from the secret rather than letting Terraform
   overwrite the new password:

   ```bash
   cd terraform/environments/{env}
   terraform plan -out plan.out
   ```

   If the plan proposes changing `master_password` back, do **not** apply it. Import the
   current value into state instead, or accept that the next intentional apply will
   re-randomise the password and repeat this procedure from step 4. Note which choice
   you made in the change record.

**Verify:**

```bash
kubectl get pods -n petclinic-{env} \
  -l 'app.kubernetes.io/name in (customers-service,visits-service,vets-service)'
kubectl logs deployment/customers-service -n petclinic-{env} --tail=50 \
  | grep -i -E "access denied|communications link failure"
```

No connection errors, and the app lists owners and vets correctly. Confirm directly with
a [debug pod](./runbook.md#procedure-connect-to-rds) if needed.

**Rollback:** Set the password back with the same `modify-db-instance` call using the
previous value, then repeat steps 4–6. Secrets Manager version history holds the old
credential document if you need to read it back.

## Rotation schedule

No automation enforces these. Track them wherever the team tracks recurring work.

| Secret | Cadence | Trigger for immediate rotation |
|--------|---------|-------------------------------|
| `petclinic/{env}/openai-api-key` | Every 90 days | Key in a commit, log, or screen share; staff change |
| `petclinic/{env}/rds-credentials` | Every 90 days | Password exposed; staff change; suspected compromise |

Also rotate immediately if a Terraform state file was exposed — the RDS password is
stored there in cleartext, which is inherent to `random_password`. The state bucket is
versioned, encrypted, blocks public access, and enforces TLS, so exposure means someone
had read access to the bucket.
